# 双缓冲数据整理与基线训练流程设计

## 1. 背景

当前仓库已经完成 `water` 缓冲下的比色皿自动裁剪、异常复核、ROI 标注与 `RGB` 导出，现有正式结果位于：

- `project_data/rgb_results/rgb_results.csv`

目前新的 `Tris=8` 条件原图已经补拍完成，原图位于 `Photo/` 下，命名形式为：

- `T=8_blank.jpg`
- `T=8_single_60,0,0.jpg`
- `T=8_binary_48,12,0_1.jpg`
- `T=8_ternary_20,20,20_2.jpg`

这意味着项目已经具备进入“双缓冲数据整理与训练骨架”阶段的条件。后续即使继续扩展到 `3` 个或 `4` 个缓冲，整体流程也不应推翻重写，而应保持：

- 图像处理流程不变
- 数据整理范式不变
- 训练目标不变
- 仅增加缓冲输入与特征列

## 2. 本次目标

本次工作目标分为四部分：

1. 让现有文件名解析规则支持 `T=8` 这类带 `=` 的缓冲名
2. 将第二个缓冲也整理为正式 `RGB` 结果表
3. 建立多缓冲统一整理层，产出长表、宽表与质控表
4. 建立基线训练层，先把双缓冲多标签训练闭环跑通

## 3. 总体原则

### 3.1 图像处理与建模解耦

现有 GUI 与 `project_data/` 继续承担“单缓冲 `RGB` 生产器”的角色，不直接承担多缓冲拼接与训练。

新增的 modeling 层负责：

- 读取多个缓冲各自的 `rgb_results.csv`
- 统一字段
- 对齐样本
- 生成训练表
- 输出基线训练结果

### 3.2 缓冲数量不写死

虽然这次先跑双缓冲，但设计必须支持后续继续接入更多缓冲。

因此：

- 输入配置采用“缓冲列表”而不是写死 `water + tris8`
- 宽表列名按缓冲前缀自动展开
- 训练脚本按配置动态读取特征列

### 3.3 样本对齐键固定

跨缓冲对齐时统一使用：

- `sample_name`
- `replicate_id`

原因：

- `sample_name` 表示同一配方
- `replicate_id` 表示同一重复编号
- 两者组合可以稳定定位“同一化学样本在不同缓冲下的观测结果”

## 4. 输入与输出

## 4.1 输入

本次 modeling 层直接读取多个单缓冲结果表，每个结果表来源于各自独立项目目录下的：

- `project_data/rgb_results/rgb_results.csv`

配置文件建议放在：

- `data_sources/buffer_sources.json`

示例结构如下：

```json
{
  "min_presence_uM": 6,
  "test_size": 0.2,
  "random_seed": 42,
  "buffers": [
    {
      "buffer_name": "water",
      "feature_prefix": "water",
      "csv_path": "project_data/rgb_results/rgb_results.csv"
    },
    {
      "buffer_name": "T=8",
      "feature_prefix": "tris8",
      "csv_path": "project_data_t8/rgb_results/rgb_results.csv"
    }
  ]
}
```

其中：

- `buffer_name` 用于保留真实缓冲名
- `feature_prefix` 用于宽表列名前缀，避免 `=` 等字符进入列名
- `csv_path` 使用相对路径，便于仓库内复用

## 4.2 输出

### 4.2.1 数据整理输出

统一放在：

- `data_processed/`

包括：

- `data_processed/buffer_rgb_long.csv`
- `data_processed/training_features_wide.csv`
- `data_processed/training_qc_summary.csv`

### 4.2.2 训练输出

统一放在：

- `model_runs/<timestamp>/`

包括：

- `model_metrics.json`
- `predictions.csv`
- `feature_columns.txt`

## 6. 标签生成规则

本项目最终目标是判断三种组分是否存在，因此训练目标继续采用多标签分类，而不是 `7` 分类。

生成规则保持与前期方案一致：

- `tc_conc_uM >= 6` -> `tc_present = 1`
- `otc_conc_uM >= 6` -> `otc_present = 1`
- `ctc_conc_uM >= 6` -> `ctc_present = 1`

否则对应标签为 `0`。

## 7. 过滤与整理规则

第一版采取保守策略，优先保证闭环稳定：

1. 同一样本在全部目标缓冲下都必须存在记录
2. 同一样本在全部目标缓冲下都必须为 `status = ok`
3. 同一个样本在同一个缓冲下若出现多条记录，先视为 `duplicate_buffer`
4. `warning` 暂不直接剔除，但要进入 `training_qc_summary.csv`

因此，进入训练宽表的样本必须满足：

- `qc_status = ready`

## 8. 基线训练设计

## 8.1 训练目标

输入：

- 多缓冲展开后的 `RGB mean/std` 特征

输出：

- `tc_present`
- `otc_present`
- `ctc_present`

## 8.2 第一版模型策略

第一版重点是跑通闭环，而不是追求最高分数。

由于当前环境只保证已有 `numpy`、`pandas` 等基础依赖，因此基线训练采用：

- NumPy 实现的 one-vs-rest 二元 Logistic Regression

这样做的优点：

- 不依赖额外安装 `scikit-learn`
- 可直接在当前仓库环境中执行
- 逻辑清晰，便于后续替换成更强模型

## 8.3 数据切分规则

训练/测试切分不能按单行随机打散，而应按 `sample_name` 分组切分。

原因：

- 同一配方不同重复之间往往非常接近
- 如果同一 `sample_name` 同时出现在训练集和测试集，结果容易虚高

因此第一版按：

- `sample_name`

做 group-based hold-out split。

## 8.4 评估指标

第一版输出以下指标：

### 单标签指标

对每个标签分别输出：

- `accuracy`
- `precision`
- `recall`
- `f1`

### 多标签整体指标

- `exact_match_ratio`
- `hamming_loss`
- `macro_f1`

## 9. `T=8` 数据接入策略

当前 `Photo/` 中已经包含 `T=8_*` 原图，但旧的文件名解析只允许字母数字缓冲名，无法识别：

- `T=8_blank.jpg`
- `T=8_binary_48,12,0.jpg`

因此本次需要同步完成两件事：

1. 调整文件名解析规则，支持 `=` 等实际命名字符
2. 提供一个非 GUI 的批处理脚本，将指定缓冲批量处理为正式项目目录

建议新增脚本：

- `run_extract_buffer.py`

其职责是：

- 从 `Photo/` 扫描图片
- 仅筛选指定缓冲
- 自动裁剪比色皿
- 复用已有 ROI 配置
- 导出该缓冲自己的 `rgb_results.csv`

输出目录建议为：

- `project_data_t8/`

这样既保留了 `Tris=8` 的正式中间产物，也不覆盖现有 `project_data/`。
